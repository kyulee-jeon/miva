# MI-VAL Validation Run — Orchestrator

MI-CDM 위에서 서로 다른 모델을 **같은 조건으로** 검증하는 전체 워크플로우를 조율한다. 개별 단계 스킬이 "무엇을 어떻게"라면, 이 스킬은 "누가 언제 어떤 순서로"다.

**실행 모드: 하이브리드.** Phase 2(순차 의존)는 에이전트 팀, Phase 3(모델별 독립)은 서브 에이전트, Phase 4(통합)는 다시 팀. 이유는 각 Phase 섹션에 적었다.

---

## Phase 0: 컨텍스트 확인

작업 전에 `_workspace/` 상태를 보고 실행 모드를 정한다.

| 상태 | 모드 | 행동 |
|------|------|------|
| `_workspace/` 없음 | **초기 실행** | Phase 1부터 전체 |
| 있음 + 부분 수정 요청 | **부분 재실행** | 해당 단계와 그 하위 단계만. 상위 단계 산출물은 재사용 |
| 있음 + 새 config/코호트 | **새 실행** | 기존을 `_workspace_prev/`로 옮기고 전체 |
| 있음 + "리포트만" | **리포트 재생성** | `05_eval_*.json`을 읽어 HTML만 다시 |

부분 재실행의 의존 관계 — 위 단계가 바뀌면 아래는 전부 무효다:

```
(1) retrieve  →  (2) profile
              →  (3) preprocess  →  (5) evaluate
                  (4) models     ↗
```

즉 retrieval spec이 바뀌면 전부 다시. 레시피만 바뀌면 (3)(5). 층화 변수만 바뀌면 (5)의 하위집단 블록만.

## Phase 1: 스터디 프로토콜 확정

**실행 모드:** 메인 (에이전트 스폰 없음)

사용자와 config를 확정한다. 이 파일 하나가 연구 프로토콜 전체다.

확인할 것:
1. **코호트** — ATLAS `cohort_definition_id`. 정의 자체는 만들지 않는다.
2. **영상 선택 규칙** — 윈도우, selection, 환자당 개수. 세 개 다 물어본다.
3. **라벨** — 대개 또 다른 ATLAS 코호트.
4. **모델** — 몇 개, 어디서, 어떤 task.
5. **DB 접근 가능 여부** — 불가하면 dry-run 모드로 진행한다.

정보가 부족하면 추측하지 말고 묻는다. 다만 **dry run은 정보가 부족해도 돌릴 수 있고**, 대개 그게 다음 질문을 구체적으로 만든다. 막히면 dry run부터.

```bash
mival dry-run -c configs/study.yaml
```

## Phase 2: 데이터 확보와 명세 (팀)

**실행 모드:** 에이전트 팀 — 세 에이전트가 순차 의존이지만 실시간 회신이 반복적으로 필요하다. 리트리버가 커버리지 경고를 보내면 프로파일러가 그걸 리포트에 반영하고, 프로파일러가 이질성을 발견하면 전처리 엔지니어가 레시피를 조정한다. 이 왕복을 배리어로 끊으면 매번 처음부터 다시 돌아야 한다.

```
TeamCreate(members=[cohort-image-retriever, data-spec-profiler, preprocess-engineer,
                    reproducibility-qa])
```

작업 순서와 의존:

1. `cohort-image-retriever` — RetrievalResult + attrition
2. `data-spec-profiler` — 데이터 명세 리포트 + **층화 변수 추천**
3. `preprocess-engineer` — 레시피 검증 + 배열 생성
4. `reproducibility-qa` — 각 단계 완료 즉시 경계면 검사 (전체 끝나고 한 번이 아니다)

모든 Agent 호출에 `model: "opus"`.

**게이트:** 커버리지가 예상보다 크게 낮거나(<50%) 메타데이터가 비어 있으면 여기서 멈추고 사용자에게 보고한다. 이 상태로 진행해서 나오는 숫자는 해석할 수 없다.

**사용자에게 중간 전달:** `_workspace/02_data_spec.html`. 모델을 돌리기 전에 데이터가 어떤지 보는 것이 이 프레임워크의 요점 중 하나다.

---

## Phase 3: 모델 통합 (서브 에이전트)

**실행 모드:** 서브 에이전트 — 모델들은 서로 독립이고, 각각의 결과만 메인으로 오면 된다. 팀 통신 오버헤드가 이득보다 크다.

```
Agent(model-integrator, model="opus", run_in_background=true)  # 모델 A
Agent(model-integrator, model="opus", run_in_background=true)  # 모델 B
```

각 에이전트는 카드 검증 + 가중치 해석 + **입력 계약 대조**를 수행한다.

**게이트:** 입력 계약 불일치가 있으면 처방(어떤 op를 추가할지)을 받아 Phase 2의 `preprocess-engineer`에게 되돌린다. 레시피 수정 후 (3)(4)를 다시 돈다. 불일치를 무시하고 진행하는 것은, 250Hz 데이터를 500Hz 모델에 먹이고 그 결과를 "일반화 실패"라고 부르는 일이다.

체크섬 불일치는 게이트가 아니라 **중단**이다.

---

## Phase 4: 평가와 종합 (팀)

**실행 모드:** 에이전트 팀 — 모든 모델의 결과를 한자리에 모아 비교표를 만들어야 하고, QA가 최종 경계면과 이식성을 검사해야 한다.

```
TeamDelete()  # Phase 2 팀 정리
TeamCreate(members=[evaluation-reporter, reproducibility-qa])
```

1. `evaluation-reporter` — 지표 산출, 층화, 비교 리포트
2. `reproducibility-qa` — 전체 경계면 체크리스트 + `mival verify`

**최종 산출물:**
- `_workspace/05_results.html` — 사용자 전달
- `_workspace/run_manifest.json` — 이식성 계약
- `_workspace/99_qa_report.json` — 검증 결과

## 데이터 전달 프로토콜

| 무엇 | 방식 |
|------|------|
| 산출물 (대용량, 감사 대상) | 파일 — `_workspace/{단계}_{에이전트}_{산출물}.{확장자}` |
| 조율 신호 (경고, 처방, 추천) | SendMessage |
| 작업 상태와 의존 | TaskCreate / TaskUpdate |
| 서브 에이전트 결과 | 반환값 |

중간 파일은 삭제하지 않는다. 사후 검증과 감사 추적이 이 프레임워크의 존재 이유다.

## 에러 핸들링

원칙: **1회 재시도 → 재실패 시 해당 결과 없이 진행하되 리포트에 누락을 명시.** 상충하는 데이터는 삭제하지 않고 두 출처를 함께 남긴다.

예외 — 다음은 재시도하지 않고 즉시 중단한다:

| 상황 | 이유 |
|------|------|
| 모델 체크섬 불일치 | 실행하려는 것이 카드가 말하는 그것이 아니다 |
| 메타데이터가 전부 빔 | 이후 모든 검증이 무의미해진다 |
| 유병률 0 또는 1 | 라벨 정의 오류일 가능성이 높다 |
| QA 실패 항목 3개 이상 | 경계면이 여러 곳에서 어긋나면 최종 숫자를 신뢰할 근거가 없다 |

부분 실패 시 리포트 상단에 "N개 모델 중 M개만 평가됨"처럼 명시한다. 조용한 축소는 "전부 다뤘다"로 읽힌다.

## 테스트 시나리오

**정상 흐름.** "STEMI 모델이랑 ECGFounder를 우리 MI-CDM으로 비교해줘"
→ Phase 1에서 config 확정(코호트 1042, ECG, index -1~0일, nearest) → dry run 통과 → Phase 2 팀 실행, 커버리지 68%, 프로파일러가 샘플링 주파수 250/500 혼재를 플래그 → 레시피에 resample 추가 → Phase 3에서 두 모델 카드 검증, ECGFounder 체크섬 확인 → Phase 4에서 두 모델 평가, 250Hz 하위집단에서 STEMI 모델 AUROC 0.54(CI 0.44-0.63) vs 500Hz 0.91(0.87-0.94) 발견 → 리포트 + 매니페스트 전달, `mival verify`는 ATLAS export 누락으로 실패 → 사용자에게 export를 요청.

**에러 흐름.** 같은 요청인데 `image_feature` 조인이 끊겨 메타데이터가 전부 빈 경우
→ Phase 2에서 리트리버가 메타데이터 0건을 감지 → 즉시 중단, 프로파일러/전처리로 넘기지 않음 → 사용자에게 "조인 경로 또는 ETL 문제로 보인다, `mival sql`로 렌더된 쿼리를 확인해달라"고 보고하고 렌더된 SQL 경로를 함께 전달 → 사용자가 수정 후 "다시 실행" → Phase 0이 `_workspace/` 존재를 감지, retrieval spec은 그대로이므로 (1)부터 재실행.

## 실행 후

사용자에게 묻는다: 결과에서 개선할 부분이 있는지, 워크플로우나 에이전트 구성에 바꾸고 싶은 점이 있는지. 답이 없으면 넘어간다.

피드백이 오면 유형에 따라 수정 대상이 다르다 — 결과 품질은 해당 단계 스킬, 역할 문제는 에이전트 정의, 순서 문제는 이 오케스트레이터, 트리거 누락은 description. 모든 변경은 `CLAUDE.md`의 변경 이력에 기록한다.
