# MI-VAL Architecture

## 왜 온톨로지인가

팔란티어의 Ontology 개념을 차용했다. 핵심은 데이터를 테이블이 아니라 **객체와 링크**로 보는 것이고, 그렇게 하면 각 단계가 "어떤 객체를 받아 어떤 객체를 내놓는가"로 정의된다.

이 프레임워크에서 그게 필요한 이유는 세 가지다.

1. **단계 교체 가능성.** 전처리 엔진을 통째로 바꿔도 `PreprocessedSample`을 내놓기만 하면 5단계는 영향받지 않는다.
2. **에이전트 구동 가능성.** 에이전트가 다음 행동을 판단하는 데 필요한 정보가 전부 객체 위에 있어야 한다. 에이전트의 머릿속이나 프롬프트에 있으면 다음 세션에서 사라진다.
3. **재현성.** 무엇이 흘렀는지를 기록할 수 없으면 재현할 수도 없다. 모든 객체가 정체성·출처·내용을 갖는 이유다.

선언형 객체(`RetrievalSpec`, `PreprocessRecipe`, `ModelCard`, `EvaluationSpec`)는 **내용의 해시가 곧 정체성**이다. 윈도우를 하루 바꾸면 `object_id`가 바뀌고, 그것이 다른 연구라는 뜻이 자동으로 드러난다.

## 계층

```
┌─────────────────────────────────────────────────────────────┐
│ ATLAS (외부)          코호트 정의 — MI-VAL은 재구현하지 않음    │
└──────────────────────────┬──────────────────────────────────┘
                           │ cohort_definition_id
┌──────────────────────────▼──────────────────────────────────┐
│ Ontology layer     CohortSpec · ImageOccurrenceRef ·        │
│                    ImageMetadata · ImageAsset · Recipe ·     │
│                    ModelCard · EvaluationSpec · RunManifest  │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│ Step modules       retrieve → profile → preprocess →        │
│                    models → evaluate                         │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│ Agent harness      6 agents + 7 skills + orchestrator        │
└─────────────────────────────────────────────────────────────┘
```

각 계층은 아래를 모른다. 에이전트 하네스를 걷어내도 Python 패키지는 그대로 동작하고, 반대로 패키지 내부를 바꿔도 에이전트 정의는 대개 그대로다.

## MI-CDM 물리 모델과의 대응

```
image_occurrence ──┬─ local_path ────────────▶ ImageAsset
                   │
                   └─ image_feature ─────────▶ ImageMetadata
                        (링크 테이블)
                          └─ measurement
                               └─ concept  (DICOM 어휘)
```

이 구현에서 스키마에 가한 조정 세 가지가 여기 반영되어 있다.

- `image_occurrence.procedure_occurrence_id`의 NOT NULL 제약 제거 — 연결된 레코드만 적재. 따라서 procedure 조인은 LEFT여야 한다.
- `image_feature.image_feature_value_order` 추가 — 리스트형 메타데이터 값의 순서 보존. 리드 순서가 여기 있고, 이걸 버리면 순서가 섞인 12-lead가 에러 없이 흘러간다.
- `image_feature.image_instance_UID` 추가 — instance 수준 추적.

## 자유도를 어떻게 확보하는가

요구사항 중 하나가 "정형화된 툴이 아니라 표준화된 쿼리를 뽑아주는 것"이었다. 설계상 세 가지 장치로 풀었다.

**1. 쿼리는 파일로 남는다.** ORM으로 숨기지 않는다. 리뷰어가 `mival sql`로 렌더된 SQL을 받아 직접 읽고 손으로 돌려볼 수 있어야 "표준화된 쿼리"라는 말이 성립한다.

**2. 결정은 필드가 된다.** "index date 근처 ECG"를 SQL에 박아 넣는 대신 `window_start_days` / `window_end_days` / `selection` 세 필드로 만든다. 애널리스트가 SQL을 손으로 고치는 순간 재현성이 끝나기 때문이다.

**3. 확장은 등록으로 한다.** 새 전처리 op는 `@register_op`, 새 로더는 `@register_loader`, 새 객체는 `registry.py` 등록. 포크하지 않고 사이트 고유 로직을 넣을 수 있다.

사용자가 바꾸는 것은 결국 config 하나다.

## 실행 모드

| 모드 | 필요한 것 | 무엇을 검증하나 |
|------|----------|----------------|
| `mival ontology` / `ops` | 없음 | 객체 그래프, 등록된 op |
| `mival sql` | config | 렌더된 쿼리 |
| `mival dry-run` | config | 쿼리 + 레시피 정적 검증 + 카드 portability + 지표 명세 + 매니페스트 |
| `mival profile` | config + DB | 1·2단계 |
| 전체 실행 | config + DB + DICOM + 모델 | 5단계 전부 |

dry-run이 존재하는 이유: PHI를 건드리기 전에 연구 프로토콜을 리뷰할 수 있어야 하고, IRB나 데이터 관리자에게 "무엇을 어떻게 뽑을 것인지"를 실행 가능한 형태로 보여줄 수 있어야 한다.

## 이식성 계약

`RunManifest`가 다음 다섯을 고정하면 다른 기관에서 같은 연구를 재실행할 수 있다.

| 대상 | 고정 방법 | 안 하면 |
|------|----------|--------|
| 코호트 | ATLAS 정의 JSON 전문 | id는 기관마다 다른 population을 가리킨다 |
| 검색 명세 | spec 해시 | 어떤 영상을 골랐는지 복원 불가 |
| 레시피 | 레시피 해시 | 전처리가 재현 불가 |
| 모델 | sha256 + 프레임워크 핀 | 가중치가 바뀌어도 모른다 |
| 지표 | spec 해시 (임계값 규칙 + 시드 포함) | 숫자가 달라져도 왜인지 모른다 |

사이트 로컬 값(`local_path_root`, `site`)은 공유 매니페스트에서 빠져야 한다 — 받는 기관이 덮어써야 하는 값이다. `mival verify`가 이 전부를 검사한다.

## 다음 확장 지점

- **CXR로 확장**: 3단계 op 레지스트리에 영상 op를 추가하는 것으로 대부분 해결된다. 1·2·5단계는 modality 무관하게 이미 동작한다.
- **다기관 실행**: 각 사이트가 같은 매니페스트로 실행하고 `EvaluationResult`만 교환하면, 데이터를 옮기지 않는 다기관 검증이 된다. 사이트별 결과를 하나로 묶는 메타 분석 계층이 다음 단계.
- **ATLAS 왕복**: 현재는 `cohort_definition_id`를 사람이 넣는다. WebAPI로 정의 JSON을 자동 export하면 이식성 검사의 가장 흔한 실패 항목이 사라진다.
- **캘리브레이션 재보정**: 기관 간 이동에서 순위는 유지되고 확률만 틀어지는 경우가 흔하다. 재보정 계층은 5단계 안에 들어갈 자리가 이미 있다.
